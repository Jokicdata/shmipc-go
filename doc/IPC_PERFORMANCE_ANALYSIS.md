# shmipc 通信方案性能对比分析

## 概述

本文档对比分析三种进程间通信方案的性能开销：

1. **原生 Socket localhost 通信** - 传统的 TCP/IP 环回机制
2. **shmipc 理想方案** - 应用主动集成，直接操作共享内存
3. **preload 劫持方案** - 通过 LD_PRELOAD 拦截 socket API

---

## 方案一：原生 Socket localhost 通信

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        原生 Socket localhost 通信                            │
└─────────────────────────────────────────────────────────────────────────────┘

【客户端】                                                        【服务端】
─────────────────────────────────                                ──────────────────────────────

  ┌──────────────┐       时间        ┌──────────────┐       时间        ┌──────────────┐
  │  App Buffer  │ ───────────────→│  Socket Buf  │ ───────────────→│  Socket Buf  │
  │ (用户空间)    │    write()      │  (内核空间)   │    TCP loopback │  (内核空间)   │
  │  0μs         │      0.1μs      │              │      5-10μs     │              │
  └──────────────┘                 └──────────────┘                 └──────────────┘
                                                                          ↓ 0.1μs
                                                                     ┌──────────────┐
                                                                     │  App Buffer  │
                                                                     │  (用户空间)   │
                                                                     │   recv()     │
                                                                     └──────────────┘

总延迟：~5-15μs (取决于消息大小)

主要开销：
  • TCP/IP 协议栈处理（协议头封装、校验和计算等）
  • 内核/用户态切换 x2（write + recv）
  • TCP loopback 数据传输
```

### 优点
- 标准化接口，兼容性好
- 内核自动处理流控、拥塞控制

### 缺点
- 数据需要经过内核协议栈处理
- 频繁的内核/用户态切换
- 内存拷贝次数较多

---

## 方案二：shmipc 理想方案（应用主动集成）

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                         shmipc 理想方案                                      │
│                      (应用直接调用 shmipc API)                               │
└─────────────────────────────────────────────────────────────────────────────┘

【客户端】                                                        【服务端】
─────────────────────────────────                                ──────────────────────────────

  ┌──────────────┐       时间        ┌──────────────┐       时间        ┌──────────────┐
  │  App Buffer  │                 │ Shared Memory│                 │ Shared Memory│
  │  (同一块!)   │ ───────────────→│  (mmap 映射) │ ───────────────→│  (mmap 映射) │
  │              │    memcpy       │              │    无需拷贝!     │              │
  │   0μs        │     0.05μs     │              │     0μs         │              │
  └──────────────┘                 └──────────────┘                 └──────────────┘
                                                                          ↓
  ┌──────────────┐                 ┌──────────────┐                 ┌──────────────┐
  │  App Buffer  │←── wakeup ──────│ Shared Memory│←── wakeup ──────│  App Buffer  │
  │              │    (epoll)      │              │    (epoll)      │              │
  │              │     0.5μs       │              │     0.5μs       │              │
  └──────────────┘                 └──────────────┘                 └──────────────┘

总延迟：~1-2μs (主要是协议通知开销)

主要开销：
  • epoll wakeup 通知 (~0.5μs x 2)
  • 共享内存映射同步

关键：应用 buffer 和 shm buffer 是同一块内存，零拷贝！
```

### 优点
- **真正的零拷贝**：应用 buffer 直接映射到共享内存
- 超低延迟：~1-2μs
- 无需内核协议栈处理

### 缺点
- 需要应用主动集成 shmipc API
- 无法透明替换现有应用

## 方案三：preload 劫持方案（当前实现）

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                         preload 劫持方案                                    │
│                     (拦截 socket API，转到 shmipc)                          │
└─────────────────────────────────────────────────────────────────────────────┘

【客户端】                                                        【服务端】
─────────────────────────────────                                ──────────────────────────────

  ┌──────────────┐  ①       ┌──────────────┐  ②       ┌──────────────┐
  │  App Buffer  │ ───────→ │  Socket Buf  │ ───────→ │  Socket Buf  │
  │  (用户空间)   │  write() │  (内核空间)   │ TCP loop│  (内核空间)   │
  │              │  0.1μs   │              │ 5-10μs  │              │
  └──────────────┘          └──────────────┘          └──────────────┘
                                                              ↓ ④
  ┌──────────────┐  ⑤       ┌──────────────┐  ⑥       ┌──────────────┐
  │  Go Runtime   │ ←─────── │ Shmipc Bridge│ ←─────── │ Shmipc Buf   │
  │  (CGO 调用)   │ C.GoBytes│  (Go 空间)   │          │  (共享内存)   │
  │              │   2μs     │              │          │              │
  └──────────────┘          └──────────────┘          └──────────────┘
         ↓                                                        ↓
  ┌──────────────┐  ⑦       ┌──────────────┐  ⑧       ┌──────────────┐
  │  App Buffer  │ ───────→ │ Shared Memory│ ────────→│ Shared Memory│
  │  (用户空间)   │ memcpy   │  (mmap)      │ memcpy   │  (mmap)      │
  │              │  0.05μs  │              │ 0.05μs  │              │
  └──────────────┘          └──────────────┘          └──────────────┘
                                                              ↓ ⑨
  ┌──────────────┐  ⑩       ┌──────────────┐                 ┌──────────────┐
  │  App Buffer  │ ←─────── │ Shmipc Bridge│                 │  App Buffer  │
  │              │ copy()  │  (Go 空间)   │                 │  (用户空间)   │
  │              │   2μs    │              │                 │              │
  └──────────────┘          └──────────────┘                 └──────────────┘

总延迟：~20-35μs (包含所有额外开销)

详细开销分解：
  ① write() 用户→内核           0.1μs
  ② TCP loopback 传输           5-10μs
  ③ recv() 内核读取             0.1μs
  ④ CGO 调用进入 Go 空间         2μs
  ⑤ C.GoBytes 拷贝 (C→Go)       2μs
  ⑥ memcpy Go→shm               0.05μs
  ⑦ epoll wakeup 通知            0.5μs
  ⑧ memcpy shm→shm              0.05μs
  ⑨ C.Copy/GoBytes 拷贝 (Go→C)  2μs
  ⑩ memcpy C→用户               0.05μs
```

### 优点
- **应用无感知**：无需修改现有应用代码
- 可以快速验证 shmipc 效果

### 缺点
- **额外的数据拷贝**：socket 数据先到内核，再被读取并拷贝到共享内存
- **CGO 开销**：每次调用都需要 CGO 边界穿越
- **无法避免内核协议栈**：TCP loopback 仍然存在

## 性能对比总结

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                            三种方案性能对比                                  │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  消息大小    原生 Socket    shmipc 理想     preload 劫持                     │
│  ───────    ──────────    ───────────    ────────────                       │
│  512B       5-8μs          1-2μs           15-20μs                          │
│  8KB        8-15μs          2-3μs           20-30μs                          │
│  256KB      50-80μs         5-10μs          60-100μs                         │
│  512KB      100-150μs       10-15μs         120-180μs                       │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│  性能分析：                                                                 │
│  • 小消息 (512B-8KB)：                                                       │
│    - preload 比原生 Socket 差 2-3 倍                                         │
│    - shmipc 理想比原生快 3-5 倍                                              │
│                                                                             │
│  • 大消息 (256KB+)：                                                        │
│    - preload 方案中，拷贝开销占比下降，略优于小消息                           │
│    - 但仍比原生 Socket 差 20-30%                                             │
│    - shmipc 理想仍然快 5-10 倍                                               │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│  preload 方案的核心问题：                                                    │
│                                                                             │
│  1. CGO 边界开销 (~2μs) - 每次调用都需要 C→Go 切换                          │
│  2. C.GoBytes 拷贝 (~2μs) - 必须将 C 内存拷贝到 Go 空间                      │
│  3. socket 数据先到内核 (~10μs) - write 系统调用先写入内核                   │
│  4. 再从内核读取并拷贝到共享内存 - 额外的内存拷贝                            │
│                                                                             │
│  而 shmipc 理想方案：                                                       │
│  1. App buffer 就是共享内存 - 无需额外拷贝                                   │
│  2. 只有 epoll wakeup 开销 (~1μs)                                           │
│  3. 直接内存映射，无内核协议栈                                               │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 结论与建议

### 为什么 preload 方案性能不理想

| 问题 | 影响 | 原因 |
|------|------|------|
| socket 数据先到内核 | +10μs | write() 系统调用特性，无法绕过 |
| CGO 边界穿越 | +2μs | C 和 Go 是不同语言，必须通过 CGO |
| C.GoBytes 拷贝 | +2μs | C 和 Go 内存空间隔离，必须拷贝 |
| 多了一次共享内存拷贝 | +0.1μs | 数据需要从 socket buffer 到 shm buffer |

**核心矛盾**：shmipc 的优势是"零拷贝"，但你的 preload 方案反而引入了**更多拷贝**。

### 什么时候 preload 方案有价值

1. **跨机器通信**：当网络延迟成为瓶颈时，shmipc 可以绕过 TCP/IP 栈
2. **大块数据传输**：减少协议栈开销
3. **高性能需求但无法修改应用**：作为临时方案

### 真正的高性能方案

| 方案 | 性能 | 代价 |
|------|------|------|
| **应用主动集成 shmipc** | 最佳 | 需要修改应用代码 |
| **eBPF 透明拦截** | 最佳 | 需要 root 权限，内核支持 |
| **内核模块** | 最佳 | 需要修改内核，开发工作量大 |
| **RDMA** | 最佳 | 需要特殊硬件 (InfiniBand/RoCE) |

### 建议

1. **如果追求极致性能**：建议应用主动集成 shmipc API
2. **如果需要透明替换**：考虑 eBPF 方案（需要环境支持）
3. **preload 方案**：适合快速验证和演示，不适合生产环境高性能场景
