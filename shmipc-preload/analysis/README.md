# shmipc-preload 性能分析与瓶颈定位方案

## 一、问题现象

| 场景 | 时延变化 | 带宽变化 |
|------|----------|----------|
| 小包 (< 8KB) | ✅ 提升 2-3x | ≈ 无差别 |
| 大包 (> 64KB) | ❌ 劣化 | ≈ 无差别 |

## 二、问题根因分析

### 2.1 核心问题：CGO 内存拷贝

在 `shmipc_bridge.go` 中存在两次额外的内存拷贝：

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                        数据流对比分析                                             │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  原始 Socket 数据流（2次拷贝）：                                                  │
│  ┌────────────┐    拷贝1    ┌────────────┐    内核传输    ┌────────────┐        │
│  │ 应用缓冲区  │ ─────────► │ 内核缓冲区  │ ═══════════► │ 内核缓冲区  │        │
│  │  (用户态)   │            │  (内核态)   │              │  (内核态)   │        │
│  └────────────┘            └────────────┘              └──────┬─────┘        │
│                                                               │               │
│                                                               │ 拷贝2         │
│                                                               ▼               │
│                                                        ┌────────────┐        │
│                                                        │ 应用缓冲区  │        │
│                                                        │  (用户态)   │        │
│                                                        └────────────┘        │
│                                                                                 │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  shmipc-preload 数据流（4次拷贝）：                                               │
│  ┌────────────┐  拷贝1   ┌────────────┐  拷贝2   ┌────────────┐               │
│  │ 应用缓冲区  │ ──────► │ C.GoBytes  │ ──────► │ Go 内存    │               │
│  │  (C 栈)    │         │ (Go 堆)    │         │ (Go 堆)    │               │
│  └────────────┘         └────────────┘         └──────┬─────┘               │
│                                                       │                       │
│                                                       │ 共享内存写入          │
│                                                       ▼                       │
│                                                ┌────────────┐               │
│                                                │ 共享内存    │ ═══════════►  │
│                                                │ (零拷贝)   │               │
│                                                └──────┬─────┘               │
│                                                       │                       │
│                                                       │ 共享内存读取          │
│                                                       ▼                       │
│                                                ┌────────────┐               │
│                                                │ Go 内存    │               │
│                                                └──────┬─────┘               │
│                                                       │ 拷贝3                 │
│                                                       ▼                       │
│                                                ┌────────────┐               │
│                                                │ Go 内存    │               │
│                                                └──────┬─────┘               │
│                                                       │ 拷贝4                 │
│                                                       ▼                       │
│                                                ┌────────────┐               │
│                                                │ 应用缓冲区  │               │
│                                                │  (C 栈)    │               │
│                                                └────────────┘               │
│                                                                                 │
│  额外开销 = 2次 CGO 内存拷贝 = 数据大小 × 2 × 内存带宽时间                        │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### 2.2 性能开销分解

| 开销项 | 小包 (1KB) | 大包 (1MB) | 说明 |
|--------|------------|------------|------|
| CGO 调用开销 | ~100ns | ~100ns | 固定开销 |
| C.GoBytes() 拷贝 | ~100ns | ~100μs | 线性增长 |
| 共享内存写入 | ~1μs | ~1ms | 零拷贝优势 |
| copy() 拷贝 | ~100ns | ~100μs | 线性增长 |
| **总额外开销** | ~300ns | ~200μs | 大包时成为瓶颈 |

### 2.3 为什么小包有优势？

```
小包场景 (1KB)：
┌────────────────────────────────────────────────────────────────────────────┐
│                                                                            │
│  原始 Socket：                                                              │
│  内核态切换 (~2μs) + 数据拷贝 (~200ns) + 内核处理 (~1μs) ≈ 3.2μs           │
│                                                                            │
│  shmipc-preload：                                                          │
│  CGO 调用 (~100ns) + 数据拷贝 (~200ns) + 共享内存 (~1μs) ≈ 1.3μs          │
│                                                                            │
│  净收益：3.2μs - 1.3μs = 1.9μs (提升 ~60%)                                 │
│                                                                            │
└────────────────────────────────────────────────────────────────────────────┘

大包场景 (1MB)：
┌────────────────────────────────────────────────────────────────────────────┐
│                                                                            │
│  原始 Socket：                                                              │
│  内核态切换 (~2μs) + 数据拷贝 (~200μs) + 内核处理 (~100μs) ≈ 302μs         │
│                                                                            │
│  shmipc-preload：                                                          │
│  CGO 调用 (~100ns) + 数据拷贝 (~200μs×2) + 共享内存 (~1μs) ≈ 401μs        │
│                                                                            │
│  净损失：401μs - 302μs = 99μs (劣化 ~33%)                                  │
│                                                                            │
└────────────────────────────────────────────────────────────────────────────┘
```

### 2.4 带宽无差别的原因

带宽测试是持续数据流，瓶颈在于：
1. **内存带宽限制**：现代 CPU 内存带宽约 20-50 GB/s
2. **CGO 额外拷贝**：虽然增加了 CPU 使用，但未触及内存带宽上限
3. **共享内存优势**：主要体现在延迟，而非带宽

## 三、性能分析方案

### 3.1 分析方法总览

| 方法 | 适用场景 | 优势 | 劣势 |
|------|----------|------|------|
| ftrace | 内核函数追踪 | 低开销，无需修改代码 | 只能追踪内核函数 |
| perf | CPU 性能分析 | 功能强大，支持火焰图 | 开销较高 |
| eBPF | 动态追踪 | 灵活，低开销 | 需要 root 权限 |
| 日志打点 | 用户态函数 | 精确，易理解 | 需要修改代码 |
| strace | 系统调用追踪 | 简单易用 | 开销大，影响结果 |

### 3.2 推荐分析流程

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                           性能分析流程                                           │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  Step 1: 确认问题                                                                │
│  ├── 运行基准测试（小包/大包）                                                   │
│  ├── 对比原始 socket vs shmipc-preload                                          │
│  └── 记录时延和带宽数据                                                          │
│                                                                                 │
│  Step 2: 定位瓶颈                                                                │
│  ├── 使用 perf 分析 CPU 热点                                                    │
│  ├── 使用 eBPF 追踪函数耗时                                                     │
│  └── 使用 strace 确认系统调用                                                   │
│                                                                                 │
│  Step 3: 细化分析                                                                │
│  ├── 添加日志打点（精确到函数级）                                                │
│  ├── 分析内存拷贝开销                                                           │
│  └── 分析 CGO 调用开销                                                          │
│                                                                                 │
│  Step 4: 验证优化                                                                │
│  ├── 实施优化方案                                                               │
│  ├── 重新运行基准测试                                                           │
│  └── 对比优化前后数据                                                           │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

## 四、具体分析工具使用

### 4.1 perf CPU 热点分析

```bash
# 分析 CPU 热点
sudo perf record -g -p <pid> -- sleep 10
sudo perf report

# 生成火焰图
sudo perf script | stackcollapse-perf.pl | flamegraph.pl > flame.svg
```

### 4.2 eBPF 函数耗时追踪

```bash
# 追踪 ShmipcWrite 函数耗时
sudo bpftrace -e '
uprobe:/path/to/libshmipc_go.so:ShmipcWrite {
    @start[tid] = nsecs;
}
uretprobe:/path/to/libshmipc_go.so:ShmipcWrite /@start[tid]/ {
    @ns[comm] = hist(nsecs - @start[tid]);
    delete(@start[tid]);
}
'
```

### 4.3 strace 系统调用分析

```bash
# 追踪系统调用
strace -T -tt -o trace.log <your-program>

# 分析系统调用耗时
grep -E "send|recv|write|read" trace.log | awk -F'[<>]' '{print $2}'
```

### 4.4 内存拷贝开销分析

```bash
# 使用 perf 分析内存操作
sudo perf stat -e cycles,instructions,cache-references,cache-misses \
    -p <pid> -- sleep 10

# 使用 eBPF 追踪 memcpy
sudo bpftrace -e '
uprobe:libc.so.6:memcpy /pid == <pid>/ {
    @memcpy[tid] = nsecs;
}
uretprobe:libc.so.6:memcpy /@memcpy[tid]/ {
    printf("memcpy: %d ns\n", nsecs - @memcpy[tid]);
    delete(@memcpy[tid]);
}
'
```

## 五、带宽分析方案

### 5.1 带宽瓶颈分析

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                           带宽瓶颈分析                                           │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  带宽 = 数据量 / 时间                                                           │
│                                                                                 │
│  理论带宽上限：                                                                  │
│  ├── 内存带宽：20-50 GB/s (DDR4/DDR5)                                          │
│  ├── CPU 缓存带宽：100-200 GB/s (L1/L2)                                        │
│  └── 共享内存带宽：接近内存带宽                                                  │
│                                                                                 │
│  实际带宽瓶颈：                                                                  │
│  ├── 应用程序处理速度                                                           │
│  ├── CGO 调用开销（每次 ~100ns）                                                │
│  ├── 内存拷贝开销（数据大小 × 内存带宽）                                         │
│  └── 锁竞争开销                                                                 │
│                                                                                 │
│  分析方法：                                                                      │
│  1. 使用 perf 分析 CPI (Cycles Per Instruction)                                │
│  2. 使用 perf 分析 cache miss rate                                             │
│  3. 使用 eBPF 分析函数调用频率                                                   │
│  4. 分析内存带宽使用情况                                                         │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### 5.2 带宽测试方法

```bash
# 使用 qperf 测试带宽
qperf 127.0.0.1 tcp_bw -m 1M -t 60

# 使用 sockperf 测试带宽
sockperf bw --tcp -i 127.0.0.1 -p 11111 -m 1M -t 60

# 监控内存带宽
sudo perf stat -e cycles,instructions,cache-references,cache-misses \
    -a -- sleep 10
```

## 六、优化方向建议

### 6.1 短期优化（不改架构）

1. **避免 C.GoBytes() 拷贝**
   - 使用 `unsafe.Slice` 直接访问 C 内存
   - 将数据直接写入共享内存

2. **避免 copy() 拷贝**
   - 使用 `unsafe.Pointer` 直接返回共享内存地址
   - 让应用程序直接读取共享内存

### 6.2 长期优化（架构改进）

1. **完全零拷贝架构**
   - 应用程序直接写入共享内存
   - 通过 UDS 仅传递元数据（地址、长度）

2. **批量处理**
   - 合并多个小包为一个大包
   - 减少 CGO 调用次数
